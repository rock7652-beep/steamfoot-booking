> **唯一正式來源（Single Source of Truth）：本文件**  
>

## 規範強度

- **MUST**：必須遵守；若要例外，需在 PR 中說明原因與影響範圍。
- **SHOULD**：原則上遵守；可因真實使用情境調整，但應保留一致性。
- **MAY**：可選做法；依模組或資料量決定。

除非條文另有標示，本文件中的「禁止／必須／不得」視為 **MUST**，「建議／優先」視為 **SHOULD**。

## 0. 強制執行原則

凡涉及蒸管家的 UI／UX、設定介面、新增功能、既有功能優化、跨模組共用元件、操作流程調整、後台桌機／iPad 介面、彈窗、設定列、清單、提醒或方案管理，執行前必須先讀取本規範，並以本規範作為設計、開發與驗收基準。

# 1. 蒸管家的產品介面原則

## 1.1 核心目標

介面應做到：**直覺、少文字、高密度、舒適、穩定。**

店長長時間操作後台，因此密度不能靠縮小字體取得，而應靠：減少不必要卡片、減少重複說明、減少垂直高度、只在需要時展開、主畫面優先顯示狀態、次要內容折疊或放進進階區。

一句話：**字不要小、畫面不要長、重點不要多。**

另一個視覺原則：**齊、短、清、穩。**

---

# 2. 四種核心介面骨架

所有新功能與設定，優先歸類到以下四種之一。

## 2.1 狀態列型

適合：目前值、開啟／關閉、目前方案、目前提醒狀態、LINE 串接狀態、系統健康狀態。

標準格式：

\`設定名稱｜目前狀態／數值｜操作\`

例：

\`預約開放｜未來 14 天｜修改\`

\`候補｜開啟・3 人・4 小時前停止｜修改\`

\`LINE 通知｜正常｜查看\`

## 2.2 編輯展開型

適合：數值設定、簡單規則、付款資料、體驗設定、預約截止、取消截止、候補規則。

原則：**平常只看狀態，點修改才展開。**

標準流程：\`查看狀態 → 修改 → 編輯 → 儲存／取消 → 收合\`

同一頁原則上只展開一項，避免整頁變成表單。

## 2.3 清單管理型

適合：人員管理、方案管理、服務管理、教室管理、位置管理、提醒方案列表、發送紀錄。

標準結構：\`搜尋｜篩選｜清單｜狀態｜操作\`

若未來可能超過 10–15 筆，設計時就必須先考慮搜尋、篩選、排序、分頁或虛擬化、批次操作。

## 2.4 預設＋例外型

適合：各方案提醒、個別方案期限、個別教練／技師設定、個別服務整理時間、個別容量、個別取消規則、個別提醒例外。

標準結構：\`店家預設 → 個別例外 → 批次套用\`

平常主表只顯示狀態，不直接攤開所有欄位。

例：\`方案｜剩餘提醒｜到期提醒｜修改\`

# 3. 三個共用核心容器

## 3.1 Settings Center

所有模組設定首頁共用。

標準結構：\`左側分類｜右側設定列表\`

每列：\`設定名稱｜目前狀態／數值｜操作\`

四模組共用同一骨架：蒸足、SPA、運動、音樂。學會一個模組，就應等於學會其他模組的設定操作。

## 3.2 Settings Panel

中型設定優先使用 Settings Panel，不要無必要跳整頁。

Settings Panel 應共用：標題、關閉按鈕、dirty guard、未儲存提示、loading 狀態、error boundary、nested navigation、panel 寬度規則、返回原位置、scroll/filter/tab 保留。

頁面選擇規則：
- 小設定 → 行內展開
- 中型設定 → Settings Panel
- 大型工作台 → 獨立頁面

## 3.3 Reminder Center

四模組提醒功能共用同一容器。

固定主分類：\`店長通知｜顧客提醒｜發送紀錄\`

各模組只注入自己的業務內容。

例：
- 蒸足：預約提醒、體驗後三階段關懷、方案提醒
- 課程：上課提醒、低額度提醒、方案到期提醒
- SPA：服務提醒、技師／位置相關通知
- 音樂：上課、請假／曠課、期數／方案提醒

共用的是操作語言，不是業務規則。

---

# 4. 設定中心分類建議

分類以 5–7 類為上限，避免過多分類。

建議方向：店家資料、營業與預約、收款與體驗、人員與權限／服務、通知與顧客經營、系統方案與用量、進階設定。

沒有內容的分類不顯示。

---

# 5. 共用設定骨架

## 5.1 Schedule Settings

適用：營業時間、特殊公休、預約開放期限、預約間隔、每時段容量。

四模組共用外框與操作節奏，保留各模組不同規則。

## 5.2 Commerce Settings

適用：銀行轉帳、付款聯繫、體驗價格、體驗可調整範圍。

共用表單外框、儲存狀態、欄位排列、錯誤處理。

## 5.3 Duty / Staff Settings

共用設定入口與狀態列。內部資料模型不硬合併：蒸足 staff、SPA spa staff、運動教練、音樂老師／教練身份。

## 5.4 Customer Growth Settings

適用：推薦分享、數位管家、顧客關懷、LINE 顧客經營。

共用外框、儲存、預覽、設定語言。

## 5.5 Subscription & Usage

適用：店家方案、系統用量、功能授權、模組功能狀態。

共用狀態顯示與入口。

---

# 6. 提醒功能規範

## 6.1 主原則

看狀態是一行，改設定才展開。不要讓 LINE 預覽搶走主操作空間。

## 6.2 方案提醒主表

標準：\`方案｜剩餘提醒｜到期提醒｜修改\`

範例：\`吉他個別課｜剩 2 堂提醒｜14、7 天前｜修改\`

不要直接在主表顯示 checkbox、數字輸入框、天數輸入框、大型預覽。

## 6.3 預覽

預覽預設收合。只有需要時：\`修改 → 查看預覽\`

預覽可用局部展開、popover、side preview。不得長期佔據主操作區。

## 6.4 批次套用

涉及大量方案時，可提供：套用到全部、套用到目前篩選結果、只套用剩餘提醒、只套用到期提醒、恢復預設。

批次操作必須清楚顯示影響範圍。

---

# 7. 設定狀態規範

所有模組統一使用：預設、自訂、開啟、關閉、已下架、未儲存、儲存中…、已儲存 ✓、需處理、功能未開通。

不得不同模組各自發明相近但不同的名稱。

---

# 8. 預設值規範

禁止：\`空白 = 系統預設\`

店長看到的應永遠是目前真正生效的值，例如 \`14 天\`、\`關閉\`、\`每 60 分鐘\`、\`3 人\`。

若使用預設值，可顯示：\`14、7 天｜預設\`

---

# 9. 開關規則

開關本身可即時儲存。

有數字／文字／天數／門檻的複合設定，需明確儲存。

關閉功能時：保留原本設定、子設定淡化或隱藏、再次開啟時恢復原值。不要因關閉功能就清空原設定。

---

# 10. 儲存與未儲存

統一規則：
- 有變更 → 顯示 \`未儲存\`
- 儲存中 → \`儲存中…\`
- 成功 → \`已儲存 ✓\`
- 錯誤 → 就地顯示

切換分類、tab、搜尋、篩選、展開其他項目、關閉 panel 時，不得讓未儲存內容無提示消失。

---

# 11. 錯誤規範

錯誤必須跟操作位置綁定。哪一列錯，就顯示在哪一列；哪一欄錯，就顯示在哪一欄。

不要只在頁面最上面顯示一個泛用錯誤。

若批次儲存部分成功：成功項目保留、失敗項目保留未儲存狀態、不整批回滾。

---

# 12. 密度與字級

密度來源：減少卡片、減少說明、減少 padding、收合低頻資訊、固定欄位、主表只看狀態。

不得靠 10–11px 小字取得密度。一般控制與設定內容建議維持約 14px 可讀性。

操作按鈕與輸入框應維持 iPad 可點擊尺寸。

---

# 13. 桌機與 iPad

後台主要驗收裝置：1366px 桌機、寬螢幕、iPad 橫向、iPad 直向。

不得只以開發者單一桌機寬度驗收。

---

# 14. 權限規範

無權限狀態必須一致。依情境選擇：可查看但不可編輯、整列不顯示、顯示「需更高權限」。

避免某頁灰掉、某頁 404、某頁直接報錯、某頁仍可點但最後失敗。

---

# 15. 空狀態

共用空狀態語言：尚未建立方案、尚未設定提醒、沒有符合條件的資料、尚無發送紀錄、尚未開通功能。

文字簡短，不需要大段教學。

---

# 16. 排序與已下架

大量管理清單：啟用中優先、自訂／需處理可提高優先、已下架淡化、已下架排後面。

列表不可每次重新整理後順序大幅變動。

---

# 17. 顏色規範

建議語意：
- 綠色：正常／成功／主要選取
- 橘色：待處理／未儲存
- 紅色：真正異常／錯誤
- 灰色：停用／已下架／次要

避免過度使用顏色。

---

# 18. 效能體感

設定頁應遵守：單筆操作不整頁刷新、可樂觀更新的操作先更新畫面、背景同步、失敗再還原、切換分類不重載整頁、即時搜尋、儲存後保留 scroll／filter／tab。

系統回應應即時給視覺回饋。

---

# 19. 頁面、Panel、行內展開判斷

### 行內展開
適合少欄位、修改快速、不需要大量上下文。

### Settings Panel
適合中型表單、多區塊、需要局部工作台、提醒管理、營業時間、體驗設定、推薦分享。

### 獨立頁面
適合大型管理工作台、需要完整寬度、大量資料、多步驟任務。

禁止無必要跳頁。

---

# 20. 設定與日常操作分離

設定中心只放「規則」，日常營運放營運頁。

例：
- 設定候補規則 → 設定
- 看今天候補名單 → 課表／營運
- 設定提醒規則 → 設定
- 查今天發送失敗 → 提醒紀錄
- 設定付款資訊 → 設定
- 今天收款 → 營運

---

# 21. 深層連結

重要設定必須有可直接定位的 URL 狀態，例如：\`section=notifications&panel=reminders\`

目的：客服可直接傳連結、操作指南可直達、教學文章可直達、新對話可直接定位、不必讓店長自己找。

---

# 22. 返回／關閉行為

關閉 panel 或返回設定時：回到原分類、保留原 tab、保留 filter、保留 scroll、不跳回設定首頁頂端。

---

# 23. 操作指南共用

操作指南優先教「共用操作」，例如看設定狀態、修改設定、儲存／取消、批次套用、未儲存提示。

各模組只補業務差異，避免四模組各寫四份幾乎相同的文章。

---

# 24. 共用元件唯一來源

共用骨架必須從共用元件庫使用。

禁止：複製一份 SettingsRow 到某模組自己改、複製一份 Panel 到某模組、複製一份 Reminder UI 再自行維護。

原則：**改一次，共用模組一起更新。**

---

# 25. 新骨架例外規則

若現有四種骨架無法適用，新增第五種之前必須回答：
1. 為什麼既有骨架不適用？
2. 其他模組未來會不會出現相同需求？
3. 這是單一例外，還是應升級成共用骨架？

不能因為「比較快」就自己做一套。

---

# 26. 危險操作

危險操作統一確認：刪除、解除綁定、清除、停用重要功能、大量覆蓋、大量批次修改。

確認視窗應清楚告知：影響什麼、影響幾筆、是否可恢復。

---

# 27. 真實情境驗收

不能只用 2–3 筆測試資料驗收。

至少驗：20–50 個方案、長名稱、大量提醒、已下架、無權限、功能未開通、空資料、錯誤狀態、慢網路、大量批次修改。

---

# 28. 可回退性

大規模 UI 共用化時優先保留資料模型、server action、業務邏輯，先換共用 UI 骨架。

避免 UI 重構同時大改資料邏輯。

---

# 29. 無障礙與操作一致性

共用 focus 狀態、Tab 順序、Escape 關閉、aria label、switch / checkbox label、錯誤訊息位置、鍵盤操作。

---

# 30. 禁止事項

禁止：
- 靠縮小字體塞資訊
- 所有設定一次攤開
- 設定中心塞日常營運功能
- 為單一模組複製共用元件
- 預覽長期佔據主操作區
- 無必要跳整頁
- 空白代表預設值
- 批次操作不顯示影響範圍
- 儲存後回到頁面最上方
- 切換分類讓未儲存資料直接消失
- 不同模組使用不同名稱描述同一操作

---

# 31. 新功能開發前四問

每個新功能開始前先回答：
1. 它屬於哪一種既有骨架？
2. 能不能使用現有共用元件？
3. 目前狀態是否能一眼看懂？
4. 資料變很多時是否仍然好用？

# 33. 開發與發布流程

固定流程：

\`需求討論 → 先讀本規範 → 選擇既有骨架 → 確認共用範圍 → 乾淨支線 → 開發 → CI → Preview → 桌機／iPad 驗收 → 使用者確認 → 明確授權 → 合併正式站 → 上線後驗收\`

未取得明確授權，不合併正式站。

---

# 34. 共用骨架與程式對應

本文件是產品規範，實作應盡量對應到共用元件，而不是只靠視覺模仿。

目前主要對應方向：

- Settings Center → `src/components/settings/`
- Settings Workspace / Nav / List Row → 共用 settings primitives
- Settings Panel → 共用 panel 容器，逐步取代只屬於單一模組的 panel wrapper
- Reminder Center → 共用 tabs、panel、dirty guard、發送紀錄與健康狀態元件
- 大量清單 → 共用搜尋／篩選／排序／批次操作模式
- 預約／課程名單 → `src/components/admin/roster-primitives.tsx`（工具列、資料列密度、狀態操作尺寸、標籤／備註欄）

若共用元件名稱或路徑改變，修改 UI 骨架的 PR **MUST** 同步檢查本節是否需要更新。

# 35. 規範版本管理

本文件需保留版本號，格式：\`UI / Settings Framework v1.x\`

每次變更需記錄：日期、變更內容、原因、影響模組。重大骨架變更才升 major version。

---

# 36. 設計決策紀錄

除了「怎麼做」，也要保留「為什麼」。

目前核心決策：
- 密度不靠縮小字體
- 大量資料主表只顯示狀態
- 修改時才展開欄位
- 預覽不佔主操作區
- 四模組共用操作骨架
- 業務規則不硬共用
- 設定與日常營運分離
- 預設值必須透明
- 大量資料先設計搜尋／篩選／批次
- 共用元件必須維持唯一來源

# 40. 全站響應式設計（RWD）

## 40.1 適用範圍與預設責任

本節適用官網、申請與登入頁、HQ、四模組後台、顧客與教練／技師前台、LINE LIFF，以及後續新增頁面與功能。新增或修改 UI 時，**MUST** 將 RWD 納入同一項工作的開發與驗收，不等待使用者再次提出「請做 RWD」。

後台主要操作裝置維持桌機與 iPad；官網與顧客／工作前台優先驗收手機。共用元件依實際使用的入口一併驗收。小螢幕後台至少能讀取資訊與操作主要控制，不要求把高密度課表全部改為手機卡片。

## 40.2 依可用空間排列

- **MUST** 依元件實際可用寬度排列；側欄、設定分類與 panel 占用的空間必須納入。嵌入式共用元件優先使用 container query，頁面外框使用既有斷點。
- 桌機維持滿版與高密度；窄寬度以換行、調整欄數、局部捲動或收合處理，禁止縮小字體或隱藏重要資訊來塞版面。
- 設定列窄版依序顯示名稱、狀態／數值與操作，寬版才排列多欄。長名稱、日期、錯誤與摘要可換行；需要截斷時須有觸控與鍵盤可用的完整資訊入口，不能只依賴 hover 或 title。
- 篩選列可換行，欄位不得超出父容器。表格、課表與時間軸可保留最小寬度，但 **MUST** 在自身區塊水平捲動，不能讓整個頁面溢出或以 overflow-hidden 裁掉資訊。
- 彈窗／右滑視窗尺寸受可見視窗限制；內容區可捲動，關閉與主要操作可到達。手機鍵盤、Safari 動態工具列與安全區不得遮住輸入及送出控制。

## 40.3 操作與狀態

- 觸控主要控制 **SHOULD** 至少 44×44 CSS px；拖曳功能 **MUST** 支援觸控，並提供鍵盤或按鈕替代。
- 功能不得只靠滑鼠 hover；浮動選單需避免被祖先容器裁切，靠近視窗邊緣時仍可使用。
- 旋轉、縮放、分割畫面或跨斷點不得清除草稿、重複提交、重置目前分類／篩選，或無提示卸載正在編輯的表單。
- 單純尺寸變化 **SHOULD** 使用 CSS，不因寬度重建整個工作台。功能權限與業務規則沿用既有檢查。

## 40.4 驗收與完成條件

每個 UI PR **MUST** 列明受影響入口、共用範圍、驗收尺寸、結果與未驗限制。

- 官網與手機前台：至少 360px／390px 寬度、長文字、鍵盤開啟與 LINE LIFF 實際入口；依受影響功能檢查 Safari 與 Chrome。
- HQ／後台：1366px 桌機、寬螢幕、1024×768 與 768×1024 iPad 尺寸；檢查側欄占用後的內容區、分割畫面與中間寬度。
- 共用元件：以受影響的各類使用位置驗收，包含頁面與窄 panel；至少檢查長名稱／摘要、展開內容、多個操作、錯誤及空狀態。
- **MUST** 檢查無整頁水平溢出、主操作可到達、文字可讀、鍵盤順序及尺寸變化後狀態保留。登入受阻、僅模擬視窗尺寸或僅用靜態 fixture 時必須如實標示，不視為真實裝置／完整業務驗收。
- 共用外框或主要操作流程的可重現回歸，**SHOULD** 加入瀏覽器自動檢查；檢查實際尺寸、溢出與操作結果，避免只比對 class 字串。
- 規範與 PR checklist 是第一層約束，不代表既有全站已通過 RWD 驗收。未驗頁面持續列入逐區盤點，不宣稱全面完成。
