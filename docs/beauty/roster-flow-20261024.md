## 延遲來源及改善

舊流程修改後 router.refresh 重跑後台 layout 與 dashboard，讀服務、技師、位置、方案、可見顧客、卡片、期間預約、收款及拆帳等資料。清單 source 物件還會隨 busy、回呼及 data 改變而觸發重讀。

新流程保留原權限、門市鎖、revision、requestKey、方案帳本、拆帳與通知交易；成功後只讀目前名單及受影響日期，回覆同一個 action。名單的讀取 effect 只依賴真正的 reader、scope、view 與明確 revision，不依賴整個 source 物件。保留背景同步，但編輯／交易期間不覆蓋草稿。

本機相同合成情境、Chromium 正式建置的一次觀察：可見完成約 648ms → 214ms；觀察區間的動作請求 5 → 1。舊紀錄另含路由預讀，不能全部當作 router.refresh；新名單異動沒有呼叫整頁更新。此為本機單次觀察，非遠端耗時保證或統計基準。新版 action 另提供 writeMs／readMs 供拆分量測，不輸出個資。

## 驗收證據

- 98 個美業／共用名單／共用改期測試檔案，820 項通過；另核對後台操作指南。
- TypeScript、相關 lint、完整 Next 建置通過；本機建置直接呼叫 Next，沒有執行 npm build 的 migration。
- 真正本機合成帳號登入 → 原清單 → action → 隔離 Postgres：出席、未出席扣／不扣、恢復、單次收款、重開未收為零、剪下貼上、取消。
- 同 requestKey 重送不新增帳本；舊 revision 拒絕；技師衝突、床位衝突皆拒絕且原預約不變；移動同行者不移動第一位。
- 低權限合成帳號實際登入：沒有收款入口，偽造出席寫入被拒，revision 不變。此本機庫沒有可用的其他店家預約，跨店邊界由既有作用域測試核對，未宣稱新增跨店真實資料驗收。
- 1366×900、1024×768、768×1024、390×844 Chromium 模擬尺寸：原列收款、主要控制可操作、無整頁水平溢出；無瀏覽器執行錯誤。
- 4 筆合成預約已經正常取消／退款，卡片回到原 7 次，這批帳本淨額 0、收退款淨額 0；歷史保留。沒有建立遠端帳號、驗證連結或分享權限。

運動／音樂仍使用同一 CourseRoster／CourseRosterList／CourseWorkspace／SportsMoveConfirm。新增 source 狀態選單、快照、行內展開及移動接點皆為可選；未提供者保留原課程 action、剪貼簿與確認行為，共用改期測試保留通過。沒有聲稱重新登入各音樂／運動真實店家驗收。
