# 預約清單讀取加速 — 2026-10-24

沿用 `preview/beauty-ui-alignment-20261021`、CourseRoster／CourseMemberWorkspace／CourseWorkspace／RightSheet。這批只處理讀取與量測，收款版面不變；不新增 schema 或 migration，LINE 關閉、正式站不動。

## 完成內容

- 顧客資料、購買方案、調整技師位置覆蓋原清單時，保留名單元件、搜尋、篩選與捲動；返回不重新掛載或完整讀名單。
- 清單開啟時暫停後方班表定時讀取。編輯、交易與子視窗期間暫停清單同步；正常背景同步先送目前版本，未變只回版本，變動才回完整資料。
- GET 名單與 POST 顧客讀取走獨立 read route，避免 React Server Action 的用戶端佇列阻塞讀取。每次重新核對登入、權限、功能與有效門市；店家參數是核對用收據，不是切換資料庫的依據。
- 版本涵蓋目前組／日期預約 revision、可讀顧客更新、相關方案與其他預約占用、到期、技師與位置名稱及所屬店長。權限變更也影響版本；不能用舊 token 跳過授權。取版本在完整 payload 前，並行寫入最多造成下一輪再核對，不會把舊資料配上新版本。
- 單一顧客的方案、預約及交易讀取限該位顧客；共卡成員仍按原可見性核對，只讀相關成員。持有方案即時權威讀取，沒有將可用次數或現金餘額改為過期快取。
- 顧客概況先讀方案；會員與 LINE 資料展開時合成一個請求，後端平行讀原服務並提供原共用面板初始資料，避免再發兩次 action。JSON 傳輸後只還原原面板實際使用的 Date 欄位。
- 私有 no-store 回覆、Server-Timing、X-Read-Trace、前端 performance.measure 與 `[BEAUTY_READ_PERF]`。固定操作名稱／隨機追蹤碼／耗時，不記姓名、電話、門市或交易內容。出席、取消、調整、收款、購買與顧客儲存保留原交易檢查；交易可分辨 db_lock 與 db_work。db_lock 包含網路往返，不能直接等同 Postgres 鎖等待。

同一台本機、正式建置、Chromium、同一隔離 Postgres 與合成顧客。前版 `938501a`；兩批合成預約在不同未占用日期，以免互相干擾。以下是少量操作觀察，**不是遠端 P95 或實體裝置保證**。原始檔在 `evidence/20261024-read-speed/`。

## 驗證與限制

- 98 檔、815 項美業／共用清單／顧客／隔離保護測試通過。先前受沙箱 EPERM 影響的子程序測試已在允許環境重跑通過。
- 真正本機帳號登入：清單原列保留、顧客概況延後會員讀取、購買方案返回、版本未變不含資料、有變只回一次新資料；沒有瀏覽器錯誤。
- 真正 Postgres：出席、恢復、同 requestKey 重送、舊 revision 拒絕、床位／技師衝突拒絕、取消及收款。扣次回復、低權限偽造寫入不改 revision；跨店收據即使附有效版本仍 403。
- 本機沒有其他店家的真實預約，跨店「外店 booking ID」案例未新增真實資料驗收；既有單元測試與讀取 API 的實際跨店收據拒絕保留。
- 桌機 1366×900、iPad 模擬 1024×768／768×1024：清單與顧客面板無整頁水平溢出。截圖只有本機合成資料。仍待實體裝置、Safari 與店家簽收。
- 音樂／運動未提供新 source port 時保留原流程；共用元件回歸通過，不代表已登入兩模組的遠端店家重驗。
- 本輪本機兩筆合成預約測試完以正常取消／退款收尾，保留歷史；清理結果另附。沒有遠端業務寫入或新增分享／登入連結。
- 最終 TypeScript、相關 lint、完整 Next 建置通過。新增顧客儲存重開（256ms）、舊版 CAS 拒絕、方案購買（211ms）／重送不新增付款／重開餘額／正常全額退款驗證；顧客原欄位值保留，新卡已關閉且餘額 0、收退款淨額 0。這些為實際本機核心驗證，未代表遠端耗時。
