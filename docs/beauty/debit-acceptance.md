## 四種規則組合

每組由真正店長建立合成3次方案、售出具名家人共用卡，顧客查權威時段並預約；依序經過：取消 → 恢復 → 未到 → 恢復 → 技師完成 → 完成後改取消 → 改未到 → 恢復 → 顧客取消。

| 取消 | 未到 | 單次取消後餘額 | 單次未到後餘額 | 恢復時餘額／預留 | 最後取消後餘額／預留 |
|---|---|---|---|---|---|
| 不扣次 | 不扣次 | 3 | 3 | 3／1 | 3／0 |
| 不扣次 | 扣次 | 3 | 2 | 3／1 | 3／0 |
| 扣次 | 不扣次 | 2 | 3 | 3／1 | 2／0 |
| 扣次 | 扣次 | 2 | 2 | 3／1 | 2／0 |

各狀態只扣該服務應扣的1次；「取消後再改未到」不累加成扣2次。每次恢復會按當前條件重新檢查，回復已扣次數並預留1次，不會把餘額變為4次。服務完成一律扣1次。

每筆預約成立後，另透過真正設定 action 將店家取消／未到規則反向切換，再執行上述流程，證實**已成立預約維持當時的規則快照**。店長、技師及顧客 RSC 的狀態／規則一致，店長及顧客的卡片餘額／預留與資料庫一致；這是實際三端資料驗收，並未把 HTTP／RSC 操作寫成逐顆按鈕或實體手機驗收。

## 帳本與拒絕情境

- 每一步驗證餘額等於 GRANT 與後續所有帳本 delta 總和，且先前帳本逐筆仍存在、內容未覆寫；只追加必要扣次或回復紀錄。
- 原完成請求原封重送，所有美業資料不變；換新 request key 卻帶舊 revision 明確拒絕。以最新 revision 再送相同完成狀態，不增加扣次、不增加服務 revision。
- 合成技師拆帳已登錄付款100元時，取消更正明確拒絕；即使交易先計算扣次回復，也完整 rollback，餘額與帳本維持完成狀態。登錄實際收回後，才成功更正。
- 另售出1次共用方案：家人已預留最後一次時，舊取消預約不能恢復；家人用完後也不能恢復或透支。家人完成再更正取消釋回1次後，才具備恢復條件。
- 即使有次數，原技師／空間時段被另一筆真正預約占用，也不能恢復；取消占用後才恢復成功。拒絕後不留下預留、扣次或半筆狀態。
- 方案取消釋回次數後完成退款結清，餘額與帳本總和為0，舊預約不能恢復使用該卡。
- 每個拒絕請求前後比對13個美業模型摘要，確認整筆回滾；全程待發通知0。
