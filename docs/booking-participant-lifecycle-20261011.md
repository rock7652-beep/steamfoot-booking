# 體驗入口改方案與撤回完成

本次修正既有會員從體驗入口預約後，選本人方案便直接完成、無法撤回的問題。

## 操作結果

| 操作 | 這位客人的狀態 | 堂數與收款 |
| --- | --- | --- |
| 改用方案 | 待到店 | 預留本人 1 堂，不扣堂、不收體驗費 |
| 完成並扣 1 堂 | 已完成 | 消耗預留堂數，新增一筆零元扣堂交易 |
| 撤回完成（方案） | 待到店 | 退回 1 堂並保留預留，原扣堂交易作廢且留稽核 |
| 取消／未到（方案） | 取消／未到 | 釋放這位客人的預留，同行者不受影響 |
| 改回體驗 | 待到店 | 釋放預留，再依體驗流程收款 |
| 撤回完成（已收體驗費） | 待到店 | 原款項保留，不等同退款；再次完成不重收 |
| 已收體驗費改方案 | 待到店 | 先作廢或全額退款，才允許改方案；交易歷史保留 |

權限、店別、本人持卡、預約日期效期、版本衝突與資料庫 guard 都由後端檢查。選方案失敗不變更狀態或丟失輸入。撤回／重做不重複發放出席點數；既有點數保留，不在此流程作財務或點數退款。

影響入口：預約明細的逐人服務操作、當日清單的完成／撤回入口、批次完成、未收款篩選、月清單方案摘要、體驗關懷資格。原預約來源仍保留，實際服務由逐人紀錄顯示。一般預約提醒不變。

## 驗證

- 11 個相關測試檔，共 143 項通過：真實 PostgreSQL 語意的 PGlite 交易／trigger、收款與同行者隔離、重試、退堂、已退款改方案、舊 guard 拒絕、授權／訂閱／開關、清單與關懷回歸。
- TypeScript、修改檔 ESLint、diff check 通過。
- 實際 React 元件的隔離 UI fixture：1366×900、1920×1080、1024×768、768×1024、390×844、360×800。各尺寸均操作改方案→完成→撤回→取消；無頁面橫向溢出，可見操作目標至少 44px，無瀏覽器程式錯誤。桌機、iPad 直向與窄螢幕截圖已檢視。
- UI 使用模擬資料，不是登入後正式站端到端驗收；交易驗證在本機隔離資料庫完成。iPadOS 真機與外部部署尚未驗證。

## 配套資料庫更新與上線順序

1. 確認目標已有逐人 schema、RLS／撤權及有效 guard；保留原函式定義及可用備份。
2. 在隔離環境套用 `docs/sql/booking-participants-lifecycle-upgrade.sql`，確認原表與原有效 guard 前置條件，以及三個更新函式仍綁定原 trigger。
3. SQL 只更新 identity／legacy／wallet guard，單一交易且有限時；不拆歷史預約、不回填、不修改客人或交易資料。審查原函式與新版差異後才部署配套應用。
4. 正式資料庫更新與正式合併仍需明確授權；此變更尚未執行這兩項。新服務調整會只讀檢查 guard 版本，未更新時回傳「服務調整更新尚未完成」，不先預留或寫稽核。
5. 外部 Preview 與正式部署各自確認選方案待到店、完成扣堂、撤回退堂及同行獨立結算。不能把 fixture 當成此驗收。

已有逐人資料的系統不能回復到不認識逐人資料的舊流程，也不能移除 guard。相容版本及原紀錄應保留。
