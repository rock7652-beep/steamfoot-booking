# 蒸足取消交易後補登正確收費

原流程只放寬已結帳日取消，之後普通新增會把補登視為今日新收款，店長因此不確定是否還需記支出或盤點調整。

現在在原購買交易取消後，直接於同一明細補登正確方案與收費。後端依原單取得交易日期，不接受前端任意指定日期；新舊單透過原交易的稽核紀錄連結。已取消的舊單也可從原明細繼續。一般新增交易仍保留原結帳日限制。

- 兩步操作：取消原交易 → 選正確方案與付款方式，確認補登。
- 堂數使用、預約、已退款等取消護欄維持。
- 補登須具 wallet.create 與 transaction.void 權限、同店同顧客，且原交易已付款並已作廢。
- 同顧客資料列鎖保護整個補登交易；相同內容重送回傳已建立的同一交易／方案，不再發堂。不同內容重送明示衝突。
- 營收、營運列表與報表按 transactionDate 計算；createdAt 保留真實操作時間供追查。
- 歷史補登不增加今日現金，不建立人工支出或盤點調整，也不改寫已實際點過的現金快照。若正確收費不同，歷史收支與舊點錢紀錄的差異仍保留供追查；本流程不代表有實際退錢或補收現金。
- 不自動配對先前透過普通新增建立的交易；不修改正式交易資料。

## 驗證

- in-memory PGlite PostgreSQL：原單 5,990 取消後補登；原日期收入還原，今日 13,197 不增加，395,085 + 13,197 = 408,282。另驗不同正確收費、相同重送與不同內容衝突。
- assignPlanToCustomer action：正確 20 堂／11,980、原交易日期、稽核連結、跨店／跨顧客／未取消／未付款拒絕、重送不再建立方案。
- 現金服務、財務報表、營運清單、原取消流程與面板回歸測試。
- 實際元件的合成瀏覽器預覽：1366×900、1024×768、768×1024、390×844、590×1000。取消→補登→成功，原日期可見，頁面無橫向溢出。桌機另驗傳輸失敗保留草稿並安全重試。使用 Chromium 模擬尺寸，非真機。
- 預覽執行：`node scripts/qa/steam-transaction-replacement-browser.mjs`，產物在 `/tmp/steam-transaction-replacement-preview`。所有 server actions 為合成回應，網路封鎖；不能當成正式資料操作驗收。
- 雲端 Preview 僅允許本精確分支，沿用原隔離資料庫、封鎖通知、跳過 migration；防護測試包含錯誤 project、repository、正式 DB 與 migration target。

不適用：大量方案重設計、效能門檻變更、其他模組交易作廢流程、正式資料修復。操作情境選測 04（交易／重送）、05（原處操作）、06（權限／顧客隔離）、07（更新報表）、08（窄畫面）、10（讀取／送出錯誤）。
