# 顧客總覽讀取改造範圍

狀態：使用者確認後已進入支線實作，尚未發布；驗收結果另見 `customer-primary-read-20261113.md`。基底為 PR #1561 / `d82a5e32d02212eaaaa2aee94e454244da085063`。目標是改善四模組顧客管理、預約名單開顧客／方案時的完整可用時間，尤其是清單剛出現就點後排顧客；不只驗已完成預讀的暖開。

## 已確認的原因

1. `use-customer-plan-preload.ts` 的 `readPlans` 等清單，再準備最多20份完整方案與日期格；`reader.read` 還等待支援資料、課程／學費等讀取。`customer-list.tsx` 以兩個顧客工作同時執行，前面的深層明細未完成時，後面的顧客主要資料也無法開始。
2. 原生 `courses/card-read/route.ts` 已將清單和進度包在同一個 HTTP 回應，但仍逐卡呼叫 `loadCourseCardProgress`。每張卡會再次查角色、顧客可見性、方案、出席、調整與購課資料，不能以 HTTP 合併視為已消除逐卡重複查詢。
3. 美業清單與日期格分開取得，後者需先知道卡號，冷開仍有先後依賴。蒸足既有抽屜已帶主要資料，應沿用其完整讀取，避免另造不相容來源。
4. 目前背景工作包含十秒重巡；指標停留／點擊可在清單工作之外啟動讀取，但沒有統一的優先權與總量管理。展開視窗會停掉尚未開始的清單排程，不能據此中止已送出的讀取。

隔離冷開補驗在固定500ms合成HTTP延遲下，各模組三次，日期格可見中位數：蒸足208ms、音樂585ms、運動596ms、美業1106ms。蒸足抽屜既有action fixture為100ms，不能跨模組比較或當成正式速度；這組數字只證明冷開仍有等待和後續請求。證據：`/tmp/customer-cold-acceptance-20261113/acceptance.md`。

正式錯誤另有 `/s/zhubei` 的 Prisma P2024 連線池逾時。現有證據不足以歸因到顧客預讀；此次不擅改連線池或資料庫環境設定。

## 修改一：定義主要畫面快照

每位顧客的主要讀取結果包含：有權檢視的有效方案第一頁、各方案完整日期格、目前可用／保留數量及期限、下次預約，以及主要畫面需要的身分狀態。姓名、電話、標籤等已在頁面props的資料直接沿用。

完整交易紀錄、歷史翻頁、詳細身分管理、課程／學費分頁和完整方案管理資料各有讀取範圍；其準備不得擋住整頁顧客的主要快照。對即將開啟的分頁或方案準備相應完整資料，不把未知餘額、隱藏欄位或佔位當成成功。

快照由同一個開窗入口消費；已準備時第一次render即顯示主要資料。首次冷開仍需讀取時保留已知身分與立即回應，主要資料齊備後一起呈現，避免多個區塊各自開始下一輪讀取。不能藉延後清單顯示來製造開窗零等待。

## 修改二：依模組提供聚合讀取

| 模組 | 實作範圍 |
| --- | --- |
| 音樂／運動 | 原授權入口增加主要快照讀取；批次取得所選顧客第一頁卡號的進度，重用原資格、可見性、共卡與進度規則。必要資訊一起回傳，不由瀏覽器再逐卡補日期格。 |
| 美業 | 透過既有原生source新增主要快照能力，合併方案、進度與下次服務的讀取；沿用美業原讀寫服務及權限，不借用課程模組的扣次／收款規則。 |
| 蒸足 | 沿用完整drawer/context讀取與wallet進度，統一清單及預約入口的準備／消費範圍；只有目前缺少且畫面需要的資料才加入，不重算錢包或改交易。 |

原生批次進度必須先核對當前使用者、門市與顧客可見性；卡號由同店授權的清單結果推導。批次取得成員、出席、調整及有權限的購課資料，再逐卡套用現有投影規則。保留既有逐卡筆數上限、異常進度與共卡成員不可見時的拒絕結果；不得將整批成功當成每卡均可讀。

每個請求內可重用權限／門市讀取，避免跨請求、跨角色快取。批次化不得透過無上限並行增加資料庫負載。先驗批次結果與原逐卡結果一致，再以實際查詢數及時間確認改善。

## 修改三：顧客專用的優先排程

1. 當頁最多20位顧客先準備主要快照，額外方案明細不得占住下一位顧客的主要讀取工作。
2. 點擊、鍵盤focus或觸控意圖提升該顧客／方案優先權；已在途的同鍵工作共用同一個promise，不能再送一份相同請求。
3. 為使用者點擊保留前景讀取容量；背景工作使用有界容量，暫停尚未開始的低優先工作。不能中斷寫入，也不假稱已取消送達後端的請求。
4. 不用十秒全量重巡持續刷新尚未開啟的深層資料。依現有異動事件、修訂、重新開啟及必要的可見性更新失效／刷新；保留15秒展示政策，不用延長TTL掩蓋等待。
5. 新排程只接顧客相關入口；月份預讀沿用原行為，避免改壞無關課表功能。

## 修改四：資料一致性與錯誤

- 範圍包含帳號／門市／模組／權限、顧客、dataScope與修訂；不持久化登入或顧客快照。
- 取得回應後先驗證範圍及失效世代，再填入完整快照與相容子快取。被作廢的晚到回應不得重新填回。
- 異動後清除受影響資料；重試取得新資料，不能因舊快照仍存在而停止刷新。錯誤及被拒絕的讀取不當成空方案或零餘額。
- 收款、扣堂、預約、身分確認等寫入繼續使用原權威檢查；展示快照不授權交易，也不改通知停發狀態。

## 驗收條件

- 四模組、顧客管理及預約名單兩個入口；測清單剛出現即點第一／第六／第二十位，以及預讀後重開、過期後重開、快速換人／換店、資料異動後返回。
- 調慢完整方案／歷史讀取，證明後排顧客主要資料仍能完成；驗證點擊優先、同鍵去重、背景總量上限，以及一個失敗不會讓其他顧客的工作停住。
- 核對預期與實際方案數、日期格、完成日期、保留／可用額度及期限；測共卡可見性、缺權限、異常進度、離線與重試。交易異動先用隔離資料／模擬回應，正式交易不因讀取驗收自行提交。
- 桌機1366×900、iPad模擬1024×768與768×1024；固定資料、角色及網路，各情境至少三次，記錄清單開始／可操作、開窗回應、完整資料可用及任務完成的中位數與範圍。
- 新鮮快照開窗不得重讀相同主要資料；冷開不得形成逐區塊後續讀取鏈。比較整條路徑，不能將等待搬到登入或清單前。毫秒門檻需依同條件基線評估，不承諾無網路讀取的首次開啟。
- 本機、整合與合成瀏覽器通過，只代表該環境；正式登入驗收仍需可用帳號或已連接瀏覽器，不能以匿名登入頁或單元測試代替。

## 實作與交付順序

先完成原生／美業主要快照及批次進度，接上顧客優先排程與原消費元件，再接蒸足與各模組預約入口；集中完成後才執行必要預覽，避免每小段都發布。保留可對照的冷／暖基線與實際SQL／HTTP數量。正式驗收登入狀態未取得前，不標記完整驗收通過。
