# 六次購買及學員方案顯示時間（2026-10-28）

> 本次上線審查版本不包含新增的驗收截圖及原始結果檔；下列 artifacts 路徑為當時紀錄的來源，並非此版本內的連結。驗收結論僅適用所載版本及條件。

使用者確認需求是音樂模組對同一學員**連續購買六次**，每次各自確認，不是一筆六期購買。以隔離 Supabase 測試店、實際登入的 Preview `0dfdb4435be9ca7f181c4047ef9b6e1148a38d7b` 測試；正式站沒有更新。

## 六次購買

每筆 10 堂、NT$1,000，付款測試方式 CARD；每次從按確認到該次購買成功回饋分別為 2,046／1,807／1,817／1,613／1,551／1,660 ms，合計等待約 10.49 秒。確認到畫面顯示方案分別為 2,052／1,813／1,826／1,621／1,559／1,665 ms。六次是在六次重新啟動瀏覽器、進購買表單後各送一次，第一筆確認至第六筆顯示合計 68.2 秒包含這些自動化啟動、頁面載入與操作間隔，不可當作店長在同一畫面連續操作的實際耗時。資料庫核對六筆 CONFIRMED、六張卡共 60 堂、六筆收入共 NT$6,000；沒有自動重送。

## 學員資料顯示

清單已就緒後，點開音樂學員的六筆方案，三次至資料顯示 1,470／1,383／1,367 ms。從完整頁面重新載入，另三次為 4,271／4,507／5,463 ms；第一輪文件請求 2,417 ms，之後期別資料 1,053 ms、購買資料約一秒，畫面需等兩者完成。同一文件請求的伺服器外框記錄約 1,608 ms；這是文件請求的一部分，不能重複加總。

運動測試店一筆方案，清單就緒後點開三次 1,450／5,341／1,367 ms，另一次測得 946／8,998／1,372 ms。8,998 ms 樣本中，第一次方案 GET 在點擊後約 85 ms 發出、耗時 963 ms；之後另有一次方案 GET。資料不足以認定第一次結果為何沒有呈現或完整歸因於哪個事件；再次的六次追蹤全在 1.36～1.96 秒，未重現該慢樣本。正式站店長當時的確切請求與瀑布時間未取得，不能把測試站的情況當作昨天的直接證據。

運動學員資料從完整頁面重新載入三次 6,420／4,700／4,140 ms；第一輪文件請求 5,026 ms，內含伺服器 layout 3,766 ms，方案 GET 後續耗時 1,140 ms。layout 紀錄中的授權、門市、試用與其他摘要有重疊，不能把各 span 相加。程式顯示 layout 要先完成多項授權、門市及營運摘要；學員方案則在畫面掛載後才開始讀取，這是此次重現的主要等待結構。

目前正式站 `979c95681a66734dfa4913ad429a1148821b6025` 的運動方案使用 Server Action，音樂期別與購買紀錄也透過 Server Action 且由 Promise.all 等待；測試站已為上述讀取採用部分獨立 GET，音樂仍需等待兩組資料後顯示。這些是可確認的程式行為，不是對昨天個別請求原因的證明。
