# 美業收費資料模型與既有資料相容方案（待確認）

本文件是建議設計，不是已執行的資料庫變更。以本機 6092de91 及尚未提交的規則核心為查核基準。未連線測試庫／正式庫、未查實際筆數、未改 Prisma schema 或 SQL、未執行 migration／重試／清資料／部署。

## 建議採最小增量模型

沿用 BeautyService 單次／體驗收費與 BeautyPlan 多次方案，不搬移既有價格、不重建方案。畫面分離不代表這階段一定要拆出新的資料表。

|資料表|建議新增欄位|用途|
|---|---|---|
|BeautyService|singleChargeName String?|獨立保存單次收費名稱，與服務名稱分開；舊資料為 null 時僅顯示服務名稱，不回寫|
|BeautyService|chargeTechnicianRule Json?|單次／體驗共用的專屬技師規則，獨立於技師服務資格|
|BeautyService|singlePriceConfigured Boolean?|區分新建服務尚未定價與明確設定免費；新建 false，收費設定成功後 true，舊資料 null 不擅自推定已確認|
|BeautyPlan|chargeTechnicianRule Json?|每個多次方案各自的技師限制；沿用既有名稱、次數、價格、期限與 serviceIds|
|BeautyCard|chargeRuleSnapshot Json?|購入時複製方案技師規則；不隨日後方案修改|
|BeautyAppointment|chargeRuleSnapshot Json?|成立預約時固定收費身分與技師規則，供改期核對；既有價格／時長／整理時間快照維持原用途|

以上為專用且版本化的業務欄位，不將名單塞入備註、稽核事件或其他既有 JSON。欄位名稱與型別須於 schema 審查定案。未產生 SQL。

## 規則格式與識別

- 所有非 null 規則須通過已實作 chargeTechnicianRule 的嚴格驗證：storeId、chargeId、revision、serviceIds、mode，SELECTED 再加 technicianIds。
- 單次／體驗共用收費身分 service:<服務ID>，多次 plan:<方案ID>；後端依已授權的資料列組合，不接受瀏覽器指定任意收費身分或門市。
- JSON 格式於儲存欄位外包版本，例如 {version:1, rule:...}；目前純核心處理 rule，持久化適配器須明確解析版本。未知版本或破損 JSON 必須阻擋，不自動降級。
- 資料庫 null 僅由相容讀取適配器依「該筆舊記錄」建立明確 LEGACY_UNRESTRICTED 規則；不能把 API 空名單、未知格式或解析失敗當成舊資料。
- 新收費寫入不可傳 null 或 LEGACY_UNRESTRICTED：必須至少一位同店、啟用、具所選服務資格的技師。
- revision 與規則內容在同一交易更新，先比較舊 revision，再保存新 revision，不能讓快照記錄錯誤版本。

## 舊資料相容矩陣

|對象／情境|建議處理|
|---|---|
|舊服務／單次價格|價格、體驗價格／分鐘原封保留；名稱 null 僅顯示服務名稱|
|舊價格為 0|維持既有營運行為；引導顯示待核對，不能當成已明確設定免費，也不能突然禁止既有預約|
|新服務未定價|singlePriceConfigured=false；可以建立服務及技師資格，但新收費入口與引導不可標成可售／完成，公開預約不得把它當成免費服務|
|舊方案技師規則為 null|沿用舊服務資格與排班規則，直到店家明確編輯並儲存新限制|
|舊多服務方案|保留全部 serviceIds，不自動縮成一項；新建方案採單一服務下拉。一般編輯不得偷偷改適用範圍，必要時保留相容編輯入口|
|已售舊卡 snapshot=null|依舊卡自身適用服務建立 legacy 規則，不取現在方案的新技師限制|
|新售卡|價格、服務、次數與技師規則同交易保存；售出後改方案不改卡|
|既有預約 snapshot=null|保留預約原價格／時間／技師／卡片；改期用原收費身分的 legacy 規則，另核對目前資格及排班，不追套最新方案限制|
|新預約|單次從服務收費規則、使用卡從該卡快照保存預約快照；不以現在方案替換卡片|
|技師停用、失去資格或休假|即使出現在快照仍不可新安排／改期；回報原因，不放寬限制，不自動取消既有預約|
|改單次收費名稱|只更新 singleChargeName，不改服務名稱、不改舊預約 serviceName|
|未有權限讀取技師／價格|不得判定成「資料為空」而覆蓋設定；由有權限者核對|

## 技師設定的兩層責任

1. 技師管理：決定技師具備哪些服務資格，以及拆帳／排班。
2. 收費方式：在具備資格的技師中，選擇該收費可安排的人。

不得呼叫既有 saveBeautyNativePlan.qualification 分支來保存方案限制，因該分支會改動 BeautyTechnician.serviceIds。新儲存需專用 action、權限／feature／門市檢查、revision 與 command 冪等控制。

## 實作與發布順序

1. 確認本資料模型與相容矩陣，補齊 null／新版本適配器與 mocked action 測試。此步仍不需任何資料庫操作。
2. 提出確切增量 SQL；只新增欄位、不 DROP／DELETE／TRUNCATE、不回填／重寫舊價格、方案或卡。實際鎖定／交易與欄位預設需納入審查，不宣稱零風險。
3. 先辨識將要操作的是測試庫或正式庫，列出確切筆數、備份涵蓋範圍、可執行的還原方法與演練結果，再請使用者確認。現在所有資料庫限制仍有效。
4. 獲准並完成測試庫結構後，接上權威讀寫與所有預約／改期入口；全路徑驗證通過才可開啟新入口。
5. 回退時先關閉新入口，保留新增欄位和資料；有 SELECTED 新資料後，舊程式會忽略限制，不能直接當成安全回退。須讓所有舊寫入入口失效，並以相容版後端持續執行限制，或暫停受影響預約寫入。另行取得部署授權。

## 本階段結論

建議新增欄位共 6 個，零資料搬移、零批次回填。這不是「實際影響 0 筆」的查核結論；尚未查資料庫，所以無法提供實際資料筆數、備份完成或不影響其他門市的實證保證。schema 可能同庫共用，新欄位雖僅由美業程式使用，仍須列出真正環境後檢查。
