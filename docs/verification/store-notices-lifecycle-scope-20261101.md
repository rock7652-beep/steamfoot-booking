# 數位管家訊息生命週期實作範圍

狀態：本文件為先前盤點快照；後續已在本機完成生命週期候選實作與隔離測試，結果以 [實作驗證紀錄](store-notices-lifecycle-20261101.md) 為準。未執行正式資料刪除、migration 或部署。依使用者確認：最新消息 3 天，歷史再 7 天，共 10 天；已讀與時間分類獨立。延續既有排序／全部已讀工作區，取代以 handledAt 區分新歷史的方案。

## 使用者看見的行為

- 兩個分頁：最新消息、歷史訊息。兩邊依訊息時間由新到舊。
- 訊息發布後未滿 72 小時屬最新；滿 72 小時到未滿 240 小時屬歷史；滿 240 小時不再顯示並進入清理範圍。兩個分頁使用同一查詢時間基準，邊界無重疊或缺漏。
- 全部標為已讀涵蓋目前門市兩分頁所有未讀訊息，清除提示、不搬動訊息、不延長有效期。
- 未讀訊息滿 3 天移入歷史時不假造已讀。滿 10 天仍依保留規則到期，未讀數量僅計算仍在保留期的訊息。
- 面板說明：「最新消息保留 3 天，之後移至歷史訊息，再保留 7 天後自動刪除。」
- 頂列採先前討論的密度調整：全部已讀與分頁同列，提示音移至標題列；窄寬可換行，字級與 44px 觸控空間保留。

## 現況與必要資料調整

三個來源：SteamfootStoreNotice、CourseStoreNotice（音樂／運動及美業 beauty 主體）、DigitalManagerNotice。共用面板為 src/components/admin/store-notice-bell.tsx，各模組讀寫 action 及 initial-store-notice-summary 皆需同步。

現有 createdAt 是資料列建立時間、startsAt 是預約／課程時間、updatedAt 會被標記操作更新。三者不能直接一律當作最新訊息發布時間：一般通知以 bookingId／subjectKey 合併更新，同筆預約今天再改期時 createdAt 仍可能是十天前。應新增明確的訊息發布時間（例如 publishedAt），只有真正業務內容異動刷新它；已讀、復原、資料維護不得刷新。必須一起涵蓋 Prisma upsert、蒸足資料庫 trigger、美業 SQL upsert、數位管家事件建立。

現有 handledAt 同時代表人工標記、業務自動完成及分頁條件，不能直接宣稱為人工讀取。新增獨立已讀時間欄位（例如 readAt），明確規劃既有資料回填以延續原提示數量；既有 handledAt、業務自動結案與事件防重仍維持原用途。單筆控制改成已讀／未讀，不再用「已處理」表示讀取；不增加預約或金流處理能力。

部署首次回填可由 createdAt 作歷史資料的保守基準，但不能用任意 updatedAt 當成新事件。需先以唯讀報告盤點舊資料筆數與已合併通知時間；明示舊訊息可能立即到期。這是待實作及驗證項目，未在本次寫入資料。

## 查詢與索引

分類與到期直接用 publishedAt 範圍查詢，不靠排程逐筆搬移，確保排程延遲時到期訊息也不繼續顯示。清單、未讀摘要、批次已讀都套相同門市、模組事件範圍與有效期。

新版時間欄位與排序、合併查詢一起設計索引；沿用索引盤點結論（store-notice-index-audit-20261101.md），先在隔離資料庫驗證 EXPLAIN，不能只新增索引就宣稱提升。不要先發布針對舊 startsAt 排序的候選索引。

## 清理排程與權限

vercel.json 已有 audit-retention，但其範圍是操作稽核，沒有通知訊息保留排程。應設獨立通知清理工作，不修改稽核保留期限。沿用 cron 認證、正式／預覽隔離、執行紀錄及失敗回報；分批刪除、短交易、有限執行時間、可重入與續跑。設定排程頻率時核對實際平台方案；畫面到期與實體清理時間分開。

美業執行角色刻意沒有 DigitalManagerNotice 的 DELETE 權限（readiness 與 SQL 測試均檢查）。不可直接擴大一般應用程式角色權限；清理需有受限的維護能力，且只處理允許的模組與到期資料。

## 必須避免的刪除副作用

recordDigitalManagerNotice 以 storeId/eventKey 唯一鍵與 ON CONFLICT DO NOTHING 防重。incomplete-service-reminders 以及美業候選查詢也用 NOT EXISTS DigitalManagerNotice 判斷是否曾產生通知。直接刪除這些列可能讓仍未完成的舊服務重新產生相同通知。

正式清理前必須設計並驗證獨立的最小防重憑據或來源到期限制，確保刪除展示內容後不重生／不重送。防重憑據不得保留完整訊息／顧客快照，且需依各事件可重試範圍定義自身生命週期，不能形成另一份無限累積的通知紀錄。僅清理通知展示紀錄，不刪預約、顧客、金流、外發佇列、操作稽核或原業務資料。

## 實作順序及驗證

1. 先實作純時間分類與資料欄位方案，準備 migration／回填報告及防重設計，不執行正式 migration。
2. 同步所有事件寫入、門市讀取／摘要／已讀 action 與共用面板；保留既有模組及角色隔離。
3. 隔離驗證 72／240 小時前後、跨午夜日期顯示、標記不續期、同預約新異動重新計時、兩來源排序分頁、全部已讀、防重、排程重跑／中斷及過期資料清理；桌機、iPad 與窄面板預覽。
4. 正式寫入與發布前提供版本、唯讀回填／刪除影響筆數及已驗證的資料庫權限方案，依使用者授權執行。
