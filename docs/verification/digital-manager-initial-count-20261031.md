- 明確條件的模擬手機：390×844、CPU slowdown 4、150ms latency、200KiB/s download。前兩次圖示至數量 2.97／3.36s，其中發出請求前的前端載入 2.25／2.55s，後端僅 142–153ms；第三次約 1.08s。此組是模擬條件，不能冒稱實體手機或 LINE 驗收。
- 因此不新增索引、不刪除權限核對，也不把 Server Action 排隊誤列為已證實主因。已證實初始數量須等待前端可執行後再另發請求；可直接消除此依賴。

## 候選實作

Dashboard layout 在原可見性與門市核對後，與既有設定／方案等讀取並行取得原模組 reader 的 summaryOnly 結果。保留 reader 的完整登入、功能、角色、門市與會員資格檢查，不新增另一套 SQL 或跨請求快取。

僅傳回同店 count／latestAt；首頁需要摘要時才開始額外等待上限 250ms，其他首頁讀取期間已完成的摘要直接使用。逾時、失敗、停用、錯店或無效數量一律不提供初始值，首頁沿用原背景流程。成功時圖示首次呈現即有權威數量，不重送同一初始請求。數量不授予處理權限；打開清單、處理／復原、focus 與定時更新仍依原流程重新讀取。只有首次掛載使用初始值，避免較舊 layout 回應蓋掉即時操作結果。

美業原本使用獨立 HTTP 讀取，維持其 transport 與動態載入；圖示載入時直接帶入同店初始數量。未更改通知內容、發送／音效偏好、跨裝置輪詢週期、收款或課程資料。

## 驗證與限制

本機 10 files／48 tests 通過：SSR 初始數量、初次不重複讀取、打開仍授權／重讀、跨店與無效值拒絕、讀取失敗／逾時後回復原流程、晚到結果無效、三模組既有操作／權限回歸。TypeScript 與變更檔 ESLint 通過。環境曾重啟，已保留既有結果並補跑中斷工作。

首次計時 Preview 在測試 fixture 的 ProcessEnv 型別上失敗，已取消該建置並改用不要求 NODE_ENV 的明確字串環境介面；修正後才做基準量測。美業轉址曾令瀏覽器量測 context 失效，無效樣本不作比較依據。最終同條件比較及 CI 結果以本次 PR 最新紀錄為準；PNG 僅留本機，不上傳登入憑證或瀏覽器狀態。

## 慢速回退追查（第二輪）

第一輪候選 `816a0c3` 桌機 6 次中 5 次初始摘要隨圖示約 17–26ms 顯示，一次回退約 0.92s；運動慢速模擬 3 次中兩次約 17–20ms，一次回退 3.145s，請求前等待 2.279s。運動、音樂、美業真實隔離 OWNER 的清單、標記與復原皆通過。此為模擬條件，不是實體裝置或正式站速度承諾。

程式確認第一輪預讀開始即倒數 250ms；即使首頁其他資料仍在載入，也已永久丟棄逾時摘要。新回歸測試重現預讀 350ms、其他首頁資料 500ms 的情境，證實首頁使用時其實已有可用結果。第二輪改為立即啟動讀取，在首頁實際使用時才計算額外等待上限；仍只讀一次，不增加跨請求快取，使用逾時後不採用晚到結果。

該 3.145s 樣本的 reader 診斷只有 117.9ms，不含延遲匯入等外圍時間，無法據此斷言就是 SQL 或匯入慢。第二輪 opt-in QA 診斷加入 `reader.import`／`reader.execute`，以及固定欄位的預讀完成、使用前是否已完成、額外等待與逾時紀錄；不記錄門市、帳號、通知內容或數量。線上同版本重測前，不宣稱此修正已解決該實測例外。
