# 原生時間欄位與多段儲存驗證

## 需求與診斷

- 接續 PR #1593，基底 `7cb0aec460d958d48776cccc93bda71b76fde163`；使用者提供 iPad 照片，指定 2026-12-17（四）及多日操作失敗。
- 最新明確決策：同一個原生時間選擇器需可鍵入小時／分鐘，不另加文字欄位或新的輸入格式。原 30／60／90／120 分鐘規則不變。
- 正式 Supabase 唯讀查核：指定店家 12/17 當日無特殊營業資料、單一時段調整或確認儲存紀錄，週四原為固定公休。不能據此斷言先前已儲存後遺失。照片第二段結束欄位空白；不完整輸入會阻擋送出，原提示不足以讓使用者辨識哪段未填。
- 未更動任何正式營業、預約、帳務、通知或資料庫結構。

## 實作

- 營業時間入口恢復單一原生 `input type=time`，每分鐘 step=60，保留鍵盤分段輸入與系統選擇器；不加自訂格式、不加替代文字欄位。保留 44px 操作範圍及窄容器寬度。
- 缺漏欄位明示第幾段、開始或結束時間，並標示尚未儲存；預覽改稱「尚未儲存的時段預覽」。
- 取得成功權威回執後，常駐顯示儲存日期與實際回傳的多段時間；切換日期時清除前一天的提示。
- 同步後台指南 B01；分支沿用停用重複預覽部署的規則，正式版本依既有發布授權處理。

## 本機結果

- 7 檔 40 項測試通過：原生控制、原有選單使用入口、多段儲存權威回執、切日／重新掛載、儲存失敗、重送、既有預約衝突與資料庫回讀。
- 真實 PGlite 執行正式 saveServiceHours：固定公休改 10:00–12:00、14:00–17:00；回傳與重新讀取均有 5 個開放起點，午休不開放。
- Chrome 本機隔離元件預覽：原生欄位實際鍵入小時 09、分鐘 30，方向鍵增至31再退回30；確認無替代文字時間欄位。缺第二段結束時間時不送出；補齊後先檢查再確認，只送出一次，兩段與5個起點立即顯示，切日、重新載入合成狀態仍完整。
- 核心流程 1366×900、1024×768、768×1024、390×844 共4組，另蒸足／課程／美業共用欄位13組回歸；無整頁水平溢出、旋轉保留草稿、失敗保留輸入。
- 程式檢查無錯誤；schedule-manager 保留2處既有 useCallback dependency 警告。diff check 通過。本機完整 TypeScript 檢查通過；遠端 CI 在發布前再次核對。
- 核心結果／截圖：`artifacts/hours-picker-save-20261124/`；共用入口結果：其 `modules/` 子目錄。瀏覽器入口為 `scripts/qa/hours-picker-save-browser.mjs`。
- 連續輸入測試初期被 Locator.press 每次重複聚焦干擾；改為一次聚焦後用 page.keyboard 連續按鍵即通過。此為測試問題，未將其誤當產品根因或引入額外同步機制。

## 限制與操作情境

- 採情境03／08及儲存後切日與回讀；未改搜尋、跨店快取、付款或排課交易，不另擴大效能驗收。Cloudflare 路由未變更。
- 瀏覽器資料／回執為合成資料，重新載入驗的是 synthetic sessionStorage；真實持久化另由 PGlite 驗證。正式店家僅唯讀核對，未寫入時段作驗收；未用真實 iPad／Safari 或店長帳號進行儲存，不能稱為該裝置的完整業務驗收。
- 指定日期尚未寫入的原因仍不能僅由照片與資料庫記錄精確還原。本次恢復原生輸入並明確區分缺漏、檢查與成功儲存，不能把先前未送出的草稿當成已恢復的正式資料。
