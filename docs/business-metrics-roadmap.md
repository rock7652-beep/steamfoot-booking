# 蒸管家經營指標 Roadmap

本 Roadmap 依據 [蒸管家經營指標規格 v1](./business-metrics-spec.md)。共同原則是：先定義，再做 query，再做 UI；一支 PR 只做一類指標。任何階段都不得為了補齊數字而猜測商業公式或直接修改 production data。

## KPI-2｜資料與定義 Audit

目標：確認每項指標是否能以現有資料可靠計算，不實作正式指標 UI。

- 盤點 Booking、Customer、Transaction、ServicePlan、CustomerPlanWallet 與 Referral 相關欄位。
- 驗證完成服務、首次完成服務、體驗、正式方案購買、退款／作廢與跨店資料品質。
- 比對 `firstVisitAt`、`convertedAt`、`lastVisitAt` 與事件資料的一致性。
- 盤點 source、referral、runtime tags 與自由文字欄位，確認是否需要結構化來源欄位。
- 為每項指標產出可行性、缺口、去重鍵、時區及歸屬規則。
- 不修改 production data；若需修復或 backfill，另開明確範圍的後續 PR。

交付順序：定義確認 → read-only audit → 資料品質報告。此階段不做 UI。

## KPI-3｜客流指標

目標：建立第一批可比較的月度客流指標。

- 本月來客數。
- 新客數。
- 舊客數。
- 體驗人數（需先確認唯一顧客或人次）。
- 本月、MoM、YoY。
- 確認店舖切分、跨店去重及人員歸屬。

交付順序：商業定義 PR → query 與資料測試 PR → 營運分析 UI PR。

## KPI-4｜開卡指標

目標：以「完成體驗當天成交」建立一致的開卡口徑。

- 開卡人數。
- 開卡率。
- 店舖時區的同一天規則。
- 有效付款、退款、取消、作廢與重複購買規則。
- 多人預約與跨店歸屬。
- 來源維度：新客來源、體驗來源、成交歸因的欄位策略。

交付順序：定義與 edge cases → query 與資料測試 → 來源維度 → UI。7 天或 30 天轉換可另列分析指標，不得混入「當天開卡率」。

## KPI-5｜留存指標

目標：在業務確認分母及觀察窗後建立留存指標。

- 回流率。
- 續約率。
- 未續約率。
- 視定義結果評估平均回店天數是否納入。
- 確認 cohort、觀察窗、方案到期、升降級與跨店規則。

交付順序：業務定義 → cohort／分母驗證 → query → UI。不得直接沿用現有 revisit 或 renewal 實作而跳過定義確認。

## KPI-6｜人員指標

目標：把已定義的全店指標安全切分到跨產業通用的「人員／服務人員」維度。

- 人員體驗人數。
- 人員開卡人數。
- 人員開卡率。
- 人員回流率。
- 延續既有人員營收並統一比較口徑。
- 確認服務人員、營收歸屬人員、顧客直屬人員衝突時的唯一規則。

交付順序：人員歸屬定義 → query 與未指派資料測試 → UI。全店指標尚未定案前，不先做對應人員率。

## 每階段完成條件

- 商業定義、分母、時間窗、時區、去重及歸屬規則已明確。
- 資料來源與 `AVAILABLE`／`PARTIAL`／`MISSING`／`TBD` 狀態已重新驗證。
- Query 有固定測試資料與 edge-case regression tests。
- UI 只呈現可靠指標，並固定顯示本月、MoM、YoY。
- 一支 PR 只做一類指標，不混入 schema 修復、資料 backfill、其他 KPI 或經營診斷解讀。
