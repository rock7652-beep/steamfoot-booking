## 回答原則

1. 先回答顧客正在問的事。預設約50～150字，不硬補到50字；複雜問題可增加，不裁切必要條件。
2. 繁體中文、親切自然、短段落、原生文字及完整HTTPS。不要把簡單問題變成規格表。
3. 利用已確認產業、人數、需求與前次推薦理解承接問句，不反覆詢問已知資料。
4. 不重複功能、試用與LINE費用。報價／購買決策當下仍須交代相關承諾期、加購、外部費用與所提優惠的條件。
5. 資訊不足時一次自然追問一題；不每次結尾都追問或推銷。
6. 推薦依需求說明原因，不主動列出所有價格與不相關模組。
7. 區分真實案例、展示、情境、指南。沒有同產業案例時坦承，不把其他產業或虛構示例冒充實店。
8. 不承諾自動轉接、通知專人、有人必回或代為聯繫。提供已核准申請／聯絡入口，與聲稱完成轉接是兩回事。
9. 不執行預約、交易、退款等營運操作；使用既有拒絕及安全機制。
10. 只共用溝通方式，不共用品牌／店家知識與顧客記憶。

50～150字是生成提示與人工品質指標，沒有新增硬截斷或第二次模型改寫。既有1200字元、512輸出token及總輸入預算不變。
`lastSources`僅代表上次引用的來源，不能推論每一條規則都已告知。沒有新增聊天逐字稿或延長記憶期限。

## 公開來源盤點

| 類別 | 核准來源 | 限制 |
| --- | --- | --- |
| 真實案例 | `/cases` 暖沐蒸足（預約提醒）、暖暖蒸足（體驗預約） | 只讀官網已公開內容；不查門市資料、不新增店家成效、聯絡資訊或參訪承諾 |
| 功能展示 | `/pricing/features/slots`、`beauty`、`fitness`、`music` | 頁面標明功能示意、範例資料，不能稱為真實客戶或可操作demo帳號 |
| 公開經營指南 | `PUBLIC_GUIDES`中published條目的標題及入口 | 不把虛構文章情境當案例，不擷取情境全文作產品承諾；draft排除 |
| 公開設定指南 | `trialGuides`及`/pricing/trial/guide/[topic]` | 只提供既有標題和入口；不傳入邀請流程、截圖憑證或個別帳號資訊 |
| 價格、試用、功能 | V2既有公開共用常數 | 不複製維護價格，不引用過期優惠或內部規格 |

目前這份核准來源中沒有美業、運動、音樂的真實店家案例，也沒有可公開分享的互動demo帳號。這不代表這些產業沒有使用者。
`PUBLIC_STORE_CASES`從原官網頁面抽出，官網與AI共用；原案例文案、選擇行為與DOM不變。AI只引用名稱與公開簡介，不擷取預約圖片中的人名、時間或個資。
來源以`customer-case`、`demonstration`、`guide`標記；仍是同一份V2來源清單、版本雜湊與稽核，不建第二套知識庫。

## 美容工作室五段品質回歸

原始問題與編輯參考回答：`src/__tests__/fixtures-brand-ai-customer-service.ts`。

| 顧客問題 | 品質目標 |
| --- | --- |
| 和太太開美容工作室、用LINE預約，適合嗎？ | 直接答適合與必要原因，不主動列全部價格；必要時僅一個需求問題 |
| 多少錢 | 延續兩人工作室，針對已推薦基本版報價，保留最低承諾；不把年繳、優惠全塞入 |
| 怎麼試用 | 提供HTTPS申請入口、必要起算／扣款規則，不再介紹全部功能 |
| 有範例嗎 | 自然釐清真實店家案例或功能示意，不以長清單代替問題 |
| 我想看實體店面的範例 | 坦承無核准美業實店案例；可明確標示其他產業的公開案例並附入口，不捏造或承諾參訪 |

本機fake Responses＋PG17.6完整reply流程驗證五輪的profile傳遞、原生sender、來源稽核與不保存逐字稿；另測錯誤／缺Key的V2提示不承諾真人轉接。
測試餵入的回答是編輯參考，不是模型實際生成。不能把fake回歸或提示詞存在，宣稱真實LLM已達到字數、相關性、不重複或語意完全正確。
