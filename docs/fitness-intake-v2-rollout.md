# 運動教室需求表單 v2：上線與驗收

## 本次範圍

- 7 題分成 3 步；四類困擾可複選、不限項數，各有其他說明。「顧客關係維護」聚焦關心、回訪與經營數據整理。
- 最優先困擾只從勾選項目選出；一項自動帶入，尚未確定跳過。
- 據點數必填單選，簡化上課與管理方式；其他需說明，尚未確定互斥。
- 不需聯絡隱藏並清除聯絡資料；伺服器與收件端再清除一次。
- 草稿、返回、錯誤定位、送出中鎖定及不確定結果禁止重送。
- 保留品牌、體驗額度、隱私告知與官方 LINE。
- 本次不是新增招生分析、鐘點費計算或 LINE 自動跟進功能。

## 資料相容性

一般店家申請與舊健檢仍要求聯絡資料、最多 3 項需求。只有
`formVersion=fitness-v2` 且 `source=fitness-intake` 使用新規則。

不改動既有試算表原始 30 欄、不刪除歷史資料、不更動兩個分頁的公式。

| 回答 | 原始資料位置／既有課程分頁 |
| --- | --- |
| 所有勾選困擾 | 原始 K：主要需求；既有課程分頁需求欄 |
| 最優先項目 | 原始 L 的「最優先改善：」與「目前流程與困擾：最優先：」；既有課程分頁「目前流程與困擾」欄 |
| 各類其他說明 | 原始 L 的「目前流程與困擾：」，沿用同名公式擷取 |
| 課程、上課方式、管理方式 | 沿用原始 L 的「課程：」「上課方式：」「管理與資料來源：」標籤 |
| 不需聯絡 | 原始 M 保留意願值，Q 狀態改為「不需聯繫」；聯絡資料欄留白 |

通知信明列最優先改善項目；不需聯絡的主旨與內文禁止主動聯繫。
舊欄位如人數、收費及空間留白是新版不再詢問，並非漏存。

## 必須依序完成，才可合併正式站

1. 更新既有 Apps Script 專案的 `scripts/store-check/Code.gs`，並把**既有** Web App 部署更新至新版本；不可另開不同接收網址。
2. GET 既有 `/exec` 回應須包含 `capabilities: ["fitness-v2", "fitness-unlimited-needs"]`（保留回應協定 `version: 2`）。只支援 `fitness-v2` 的舊收件端仍限四項，不可直接合併這次不限項數的網站更新。
3. 在預覽完成手機 375px／390px 及桌機實際點選與視覺驗收。
4. 使用隔離／mock 收件端完成送出成功、失敗及重送保護驗收；若需要正式試算表測試，先確認測試資料範圍。
5. CI 通過，再確認合併正式站。此次未合併、未提交正式測試資料。

新 API 每次新版送出前會先 GET 檢查能力。若不支援或讀取失敗，**不會 POST**，回傳
503 `RECEIVER_UPDATE_REQUIRED`；前端保留草稿且允許稍後重試。超過四項另檢查 `fitness-unlimited-needs`，避免舊收件端拒收。POST 結果不明則維持鎖定，禁止自動重試。

## 程式驗證

```sh
npm ci
npx vitest run src/__tests__/fitness-intake-ui.test.ts src/__tests__/store-check-submit.test.ts src/__tests__/store-check-receiver.test.ts
node --check public/pricing/fitness.js
git diff --check
```

DOM 互動測試使用 jsdom，不代表真實 Safari／Chrome 或手機版視覺驗收。
本次驗收瀏覽器 `refresh tabs` 連線逾時，因此真實手機／桌機視覺仍待補驗。
本機全專案 `tsc --noEmit` 受缺少 `generated/spa-client` 與既有 Prisma 產生型別不一致影響，未通過；不可視為完整 build 通過。本次修改的 API 與三份測試另做獨立型別檢查與 ESLint。

## 手機驗收清單

- 375／390px 無水平溢位；文字不切斷、勾選區易點；綠金品牌一致。
- 第 5 個及其餘困擾都能勾入，顯示「已選 N 項」，沒有上限、分母或更換提示；全部 19 項也能送出並完整保存。
- 四類其他欄位展開、必填提示與返回位置正確。
- 更換困擾後清除失效優先項；單一困擾不重問；未確定互斥。
- 返回與重開同一分頁保留草稿，舊版未確認送出不得繞過重送保護。
- 選不需聯絡後不再傳送已輸入聯絡資訊；改回申請體驗會重新要求聯絡資料。
- 收件端未升級、送出中、回應失聯與成功畫面皆符合實際保存狀態。
