## 後續：美業時段兩項失敗已釐清並修正

使用者同意先釐清兩項失敗，再確認這批修改是否適合發布；這項同意沒有擴及正式部署或正式資料操作。

原因：查詢先把 `startsAt` 轉成台灣日期，再強制轉成無時區 `timestamp`。本機測試使用的 PGlite 在 Asia/Taipei 環境會把 `2030-10-10 00:00` 讀成 `2030-10-09T16:00:00Z`，後續以 UTC 日期取營業日及星期，導致查錯前一天。相同舊版本在 UTC 時區的 12 項測試全部通過，確認此失敗與程序時區有關；不是本輪即時篩選引入，也不能據此認定正式 Prisma 環境已有相同漏擋。

修正：`src/server/services/service-hours-save.ts` 移除多餘的 `::timestamp`，讓台灣營業日以 PostgreSQL 原生 `date` 回傳，與既有 `bookingDate` 日期欄位約定一致；預約起訖、完整佔用時長、門市範圍、鎖定及原子儲存規則不變。沒有 schema／migration／索引變更。

新增測試以台灣凌晨 00:15 的美業預約調整星期五營業時間：必須拒絕衝突、回傳正確台灣日期，而且營業設定與 AuditLog 都不留下部分寫入。保留原有佔用到 11:15、停用 11:00 時段、多星期批次、例外日期與容量、冪等重送等案例。

- Asia/Taipei：13／13 通過，見 [台灣時區](evidence/20261114-instant-filters/hours-taipei-fixed.log)。
- UTC：相關營業／可預約時段與門市範圍 74／74 通過，見 [UTC](evidence/20261114-instant-filters/hours-utc-fixed.log)。
- America/New_York：13／13 通過，見 [紐約時區](evidence/20261114-instant-filters/hours-newyork-fixed.log)。
- 舊版本 UTC 基準：12／12 通過，見 [UTC 基準](evidence/20261114-instant-filters/baseline-hours-utc.log)，與原本台灣環境 2 項失敗形成對照。
- 兩個修改檔案 ESLint、完整 TypeScript 與 diff 格式檢查通過。均為本機合成資料／PGlite 驗證，未在正式站修改營業時間或預約。

最終整套回歸（`TZ=Asia/Taipei node node_modules/vitest/vitest.mjs run`）：**1,815 個檔案、17,067 項通過，334 項跳過、0 失敗**，見 [最終完整紀錄](evidence/20261114-instant-filters/full-tests-fixed-final.log)。整合本輪即時篩選與美業日期型別修正後執行，原兩項失敗均已消除。完整 TypeScript、變更檔案 ESLint 及 diff 格式檢查通過；剩餘 334 項跳過仍不計為通過。

結論：本機修改與適用檢查已完成，可進入發布流程。尚未進行本輪遠端版本核對、Preview 全入口業務驗收、正式合併／部署或正式資料寫入，不能以全量本機測試通過代替正式站可用證據。

## 正式查核補修：清除後再次搜尋（同輪發布授權）

PR #1568 的正式部署 `dpl_CjTj8b8mNJro5At1dcdmMv3C1eYu` 已發布至 www。正式唯讀查核發現：期間消耗按清除會恢復 234 人，但再次搜尋時可能帶回先前的店長與數值條件。此情況未被前一輪只查「清除後結果筆數」的案例涵蓋，不能僅依畫面恢復就宣稱完整清除成功。

原因為外部導航途中用舊 props 重新渲染，就先消耗了共用表單的還原標記；隱藏條件仍留在 client 草稿。另補查原生 reset 後再次貼上相同文字及排序還原。

補修內容：
- 共用表單可傳入 server filters 的 navigationKey，等新查詢條件確認後才執行草稿還原；不讓中途舊 props 誤消耗標記。顧客消費紀錄同樣接入。
- 期間消耗的清除動作立即清掉關鍵字、收費方式、日期模式、所屬店長、前 N 名、扣除條件與全部數值條件，再同步 server 結果；排序依重設後的表單還原。
- 原生 form reset 後同步輸入事件追蹤，確保再次貼上相同文字也能自動查詢。

新增三項回歸：已套用條件清除時穿插舊 props render、尚未收到伺服器回應就清除進階草稿，以及清除後重貼相同關鍵字。修正前能重現失敗，見 [失敗重現](evidence/20261114-instant-filters/clear-regression-before.log)；修正後通過，見 [回歸](evidence/20261114-instant-filters/clear-regression-after.log)。專項 492 通過／36 跳過，完整 TypeScript 與變更檔案 ESLint 通過。

本機實際元件預覽亦驗證：同一關鍵字＋實付由少到多＋最低 3 次＋所屬店長，清除後欄位及排序回到預設，再貼同一關鍵字，實際送出的查詢不含 staffId、count_min 或其他舊條件。預覽使用合成資料，不替代補修正式部署後的同路徑查核。此補修不含交易、資料庫或通知設定變更。
