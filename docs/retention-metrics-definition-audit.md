# 留存指標定義 Audit

> 留存回答「顧客有沒有再次回來接受服務」；續約回答「顧客有沒有再次購買方案」。兩者相關，但不可混成同一個數字。

## 範圍與原則

本文件只盤點定義與資料，不定案公式、不撰寫 Query，也不修改 UI、DB 或正式資料。指標須跨產業適用，使用「顧客、服務、方案、回流、續約、人員、店舖」，不使用特定產業術語或由工程自行設定固定 7／30／60 天門檻。

## Repository 現況盤點

### 已存在的報表公式

`src/server/services/advanced-reports.ts` 與經營診斷頁目前已有兩個同名概念，但只能視為既有產品口徑：

- `revisit`／「回訪率」：分母是指定店舖在觀察期開始前曾有任一 `COMPLETED` Booking 的所有唯一顧客；分子是其中在本期也有 `COMPLETED` Booking 的顧客。這不是本文件 A（本月客群結構）、B（上月 cohort）或 C（應回流 cohort）的完整等價口徑；觀察歷史愈長，分母愈容易累積。
- `renewal`／「續購率」：先找本期建立 Wallet 的唯一購買顧客作分母，再以本期以前是否已有 Wallet 判斷分子。它回答「本期購買者中有多少是曾購買者」，不是「有續約資格者中有多少續約」。未檢查 Wallet 到期、用完、取消、退款或續約視窗。
- 測試只鎖定上述程式行為，不代表商業定義已獲確認。既有 UI 名稱也不能當作正式指標定義。

### 顧客經營提醒不是留存公式

- 「好久不見」目前以完成服務紀錄搭配 30 天門檻形成追蹤清單。
- 「方案快到期」目前使用 14 天門檻。
- 其他頁面另有 30／60／90 天 active、inactive、dormant 分群。

這些門檻服務 CRM 提醒與畫面分類；不同頁面目的及門檻不同，不能直接視為回流率、未回流人數或續約率公式。

### 資料結構與品質

| 資料 | 現況 | 留存用途與限制 |
| --- | --- | --- |
| `Booking` | 有 `customerId`、`storeId`、純日期 `bookingDate`、`bookingStatus`、人員欄位；狀態包含 `COMPLETED`、`CANCELLED`、`NO_SHOW` | `COMPLETED` Booking 是目前最可靠的服務完成事件。沒有獨立「完成時間」timestamp，應以 `bookingDate` 作服務日；同日多筆是否先去重仍待定義。歷史 Booking 完整性需另以資料抽樣驗證。 |
| `Customer.firstVisitAt` | nullable；repository 未找到正式服務完成流程持續寫入 | 可顯示或交叉驗證，不足以單獨作首次完成服務真相。KPI 應以 Booking 歷史重建。 |
| `Customer.lastVisitAt` | nullable；多個查詢直接使用，但顧客列表另以 Booking 結果覆蓋 stale 舊值，且已有 regression test 明載 stale/null 情境 | 不能作正式回流 KPI 的唯一資料源。 |
| `Customer.convertedAt` | 首次購買方案流程會寫入，但 nullable，且既有資料與退款後狀態未保證同步 | 不代表續約，也不應用於續約資格或目前有效權益判斷。 |
| `Customer.customerStage` | `LEAD`／`TRIAL`／`ACTIVE`／`INACTIVE` 等營運階段 | 是 CRM 狀態，不是事件；更新完整性與門檻不等同留存定義。 |
| `CustomerPlanWallet` | 有 customer、store、plan、start／expiry date、總／剩餘堂數、`ACTIVE`／`USED_UP`／`EXPIRED`／`CANCELLED` 與 createdAt | 可支援方案生命週期候選 cohort，但需先決定到期、用完、取消及多 Wallet 規則。`remainingSessions` 是快取欄位；需搭配 WalletSession／退款流程判讀。 |
| `Transaction` | 有 `PACKAGE_PURCHASE`、付款與交易狀態、交易日、Wallet 關聯、退款反向關係 | 可辨識再次成功購買；schema 沒有 `PACKAGE_RENEWAL`，續約必須由事件序列推導。全額退款後權益取消應以 Wallet 狀態為主要依據，不能只看退款金額。 |
| 顧客合併 | source row 以 `mergedIntoCustomerId` 封存，FK 搬到 target；不允許跨店合併 | 新 Query 必須排除／解析 merged source，否則可能重複計算。既有 advanced reports 沒有明示 merged-source 過濾，需在實作前另驗。 |
| `CustomerIdentityLink` | 每店一筆 store-scoped identity link，可把同一 `userId` 對應到各店 Customer | 只對已建立且同步成功的身份連結有效，不能假設覆蓋所有歷史顧客；HQ 去重資料信心不足。 |

## 回流人數候選定義

| 方案 | 定義 | 優點 | 限制 |
| --- | --- | --- | --- |
| A：本月舊客數 | 本月有 `COMPLETED` Booking，且本月以前已有 `COMPLETED` Booking 的唯一顧客數 | 現有 Booking 可可靠計算；與 KPI-3 舊客數一致 | 比較像本月舊客人數，不是 cohort 留存；若再做 KPI-5B 只會重複既有指標 |
| B：上月 cohort 回流 | 上月有 `COMPLETED` Booking 的唯一顧客中，本月也完成服務者 | 分子、分母與月份清楚；可衡量連續月回流 | 對回店週期超過一個月的產業不公平；季節性亦會影響解讀 |
| C：應回流 cohort | 觀察窗內符合「應回流」條件的顧客中，本期完成服務者 | 最接近經營上的留存 | 必須先定義應回流資格、觀察窗、服務／方案週期；現有結構可能不足 |

三種方案回答不同問題，本 PR 不替業務端選定。

## 回流率候選定義

| 方案 | 分子 ÷ 分母 | 解讀 |
| --- | --- | --- |
| A | 本月舊客數 ÷ 本月來客數 | 是本月客群結構中的舊客占比，不是真正 retention rate。 |
| B | 上月來客中，本月再次完成服務人數 ÷ 上月來客數 | 是月對月 cohort 回流，但高度受產業回店週期影響。 |
| C | 應回流顧客中，本期完成服務人數 ÷ 應回流顧客數 | 最接近留存，但要先成熟定義觀察窗與應回流規則。 |

現有 advanced reports 的分母是「本期以前所有歷史曾完成服務顧客」，應單獨標為 legacy 口徑，不能當成 A、B 或 C 已定案。

## 未回流人數候選定義

- A：上月有完成服務、但本月未再次完成服務的唯一顧客數。
- B：符合應回流條件、但本期沒有完成服務的唯一顧客數。
- C：距最後一次完成服務已超過 N 天的顧客數。

方案 C 的 N 天不得由工程設定；它可能依產業、服務與方案週期不同。現有「好久不見」門檻只是顧客經營提醒，不能直接成為正式 KPI。未回流也不一定等於流失；顧客可能仍在合理服務週期內。

## 續約與未續約候選定義

### 可用事件

- 正式方案購買可由成功的 `PACKAGE_PURCHASE` Transaction 與其 Wallet 關聯辨識。
- Wallet 有開始日、到期日、剩餘堂數與狀態；WalletSession 能補充堂數實際使用狀態。
- schema 沒有 `PACKAGE_RENEWAL`，再次購買是否為續約必須依前後方案／Wallet 關係推導。
- `CANCELLED`、退款／作廢與 payment status 必須排除；部分退款但權益保留不能簡化成未續約。

### 候選分母

1. 本月到期方案數。
2. 本月用完方案數。
3. 本月符合「到期或用完」的唯一顧客數。
4. 符合正式續約資格規則的唯一顧客數。

方案數會讓同一顧客的多 Wallet 重複；顧客數則會掩蓋方案別結果。到期日為 null、提前用完、已取消、部分退款及方案重疊均需明確處理。

### 候選分子／續約視窗

- 同日再次購買正式方案。
- 原方案到期前再次購買。
- 到期或用完後 N 天內再次購買。
- 任意時間再次購買正式方案。

N 天不可由工程定案。「任意時間」較像重購而非續約。未續約人數／率只能在續約資格與觀察窗完整結束後成立，不能過早以 `1 - 續約率` 標記仍在等待期的顧客。

### 必須由業務確認

- 續約以方案、Wallet 還是唯一顧客為單位。
- 同一顧客同時有多個方案／重疊 Wallet 時的資格與去重。
- 部分退款是否影響續約資格；全額退款／取消如何排除。
- 換方案、升降級是否算續約。
- A 店購買、B 店使用或再次購買時的歸屬。
- 續約視窗起點、終點與 N 天。

## 平均回店天數候選定義

候選公式是同一顧客相鄰兩次 `COMPLETED` Booking 的日期間隔平均。Booking 足以產生候選間隔，但商業定義尚未完成，暫不實作。

需確認：

- 先算每位顧客平均後再平均，或直接平均所有相鄰間隔。
- 是否排除首次體驗到首次正式服務。
- 是否排除異常長間隔，若排除則門檻由誰決定。
- 單店隔離或跨店合併。
- 同日多次服務算 0 天，或先依顧客／日期去重。
- 觀察期邊界外的前一次服務是否納入。

## 店舖、人員與跨店歸屬

- 單店回流可以 `storeId` 隔離 Booking；此口徑最可控。
- 人員回流需先決定歸屬人員、實際服務人員或每次服務人員，不能在全店公式以前定案。
- `CustomerIdentityLink` 理論上可藉共同 `userId` 串聯各店 Customer，但只覆蓋已綁定身份，歷史與未登入顧客仍可能缺漏，因此 HQ all-store 暫不能可靠去重。
- 顧客在 A 店首次服務、B 店回訪，要歸 A、B、兩者或品牌層，屬業務決策。
- A 店購買、B 店使用／續購的續約歸屬也未定；購買店、使用店與顧客歸屬店可能不同。
- 店內顧客合併會把 FK 移至 target，但 source row 保留；所有未來 KPI 都需 canonical customer 規則。

## 待業務確認

1. 回流率採 A、B、C，或另訂 cohort／服務週期口徑。
2. 「應回流」的資格、觀察窗及是否依方案／服務類型不同。
3. 未回流何時成立，及 N 天是否依產業、方案或服務調整。
4. 續約的統計單位、資格分母與續約視窗。
5. 多 Wallet、重疊方案、換方案、升降級、退款與取消規則。
6. 平均回店天數的平均方法、同日去重與異常值政策。
7. 人員回流歸屬使用 assigned、service 或 revenue staff。
8. 單店、跨店與 HQ 品牌層顧客的 identity 與歸屬。
9. 歷史 Booking／Wallet／Transaction 完整性的資料抽樣標準。

## 建議

1. **最適合先開發**：若業務接受方案 B，KPI-5B 可只做「上月來客本月回流人數、上月 cohort 回流率、未回流人數」，因 Booking 事件與月份邊界最清楚；但必須先正式批准 B 及其適用情境。
2. **可用現有 Booking 的項目**：方案 A 舊客數、方案 B 的回流／未回流 cohort，以及平均回店間隔的原始資料。A 已在 KPI-3，無需換名稱重做；其餘仍需商業定義。
3. **定義前不可開發**：方案 C、正式續約／未續約、平均回店天數、人員回流率、跨店／HQ 回流率。
4. **可能需要結構化欄位**：應回流日期／週期、續約資格與視窗、前後 Wallet／方案關係、跨店 canonical customer。是否新增須待後續資料設計 PR，不在本 PR 處理。
5. **KPI-5B 最小 Scope**：先由業務選定回流 B；若選定，僅做單店與 viewed store 的三個 Booking cohort 指標及 MoM／YoY，不做續約、平均天數、人員或 HQ。若 B 未獲批准，KPI-5B 應暫停，不應重複 KPI-3 的「舊客數」。
