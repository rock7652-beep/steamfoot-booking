# 美業方案加速更新：本機隔離驗收

以 `1e0ae2d6` 加尚未提交的同步修改測試；具體 hook SHA-256 存於 `results.json`。本機使用一次性 PostgreSQL、合成美業店及 3 位合成會員；會員與店長分別透過 Auth.js 實際登入不同 Chromium context，購買意圖僅本機啟用，通知停用。

3 輪中，由店長核帳完成提示至會員顯示 1 個方案分別為 **794、797、811 毫秒**；導致更新的方案快照請求分別約 **52、48、152 毫秒**。每輪核對 1 訂單、1 方案卡及 1 筆 SALE，會員文件未重載；結果與每次請求的時點與延遲見 `results.json`。首輪另有 1 次較早的快照請求耗時 4,682 毫秒。樣本少、皆在本機且待核帳後很快核帳，不代表正式站或網路環境的速度。

新策略僅在前景方案頁觀察到新待核帳後加速 60 秒：每次讀取完成後等待 2 秒再查，失敗退避；之後回到 10 秒。加上網路及查詢時間，不能保證 2 秒內更新，也不是事件推播。以 1,000 位同時處於加速期的會員計，理論上約每秒 500 次快照請求；尚無負載或成本量測。

背景分頁實測見 `background.json`：Headless Chromium 中切換分頁後，會員頁仍回報 `visibilityState=visible`，測試停止，未驗證真實背景／前景復原。此樣本有建立一筆額外合成待核帳，但全部資料庫將於驗收結束後移除。

未驗證：同版本線上環境、真實 LINE LIFF／Safari、真實裝置、權限撤銷及斷線重連的端到端行為。後台與會員的正式資料均未使用。
