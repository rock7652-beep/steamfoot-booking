# 美業購買核對：本機登入驗收

候選版本 `019c8893`，僅使用本機獨立 PostgreSQL、合成店、會員、店長與測試方案。伺服器啟用會員及後台意圖旗標，通知關閉。瀏覽器使用實際 Auth.js 登入及實際 Server Actions；不是 LINE LIFF、Safari 或實機驗收。

- 正常流程腳本執行輸出 `complete:true, checks:10`：會員建立 1 筆待核帳訂單且卡／收款／帳務沒有增加；重整後找回申請並確認；店長核帳後增加 1 張卡、1 筆 SALE、1 筆現金帳，方案次數及金額與測試方案一致，再確認結果。原測試店已有 2 筆其他合成 SALE；核對使用前後差值。桌機 1366×900、iPad 1024×768 和 768×1024 及手機 360px 在當時頁面無整頁橫向溢出，不等同完整彈窗或實機驗收。
- 正常流程截圖是在店長確認後立即拍攝，後台當時仍顯示「正在核對」，會員頁仍顯示原有 0 個方案；本次未等待兩側畫面完成同步，也未驗證會員重新載入後方案顯示。不能憑資料庫已發卡宣稱跨裝置即時同步或前台顯示已通過。
- [races.json](races.json)：伺服器成功後刻意丟棄回應，產生 1 筆訂單；重整可找回。第二個情境在另一分頁取消後放行原請求，當時訂單增加 0 筆；此筆未等待回應結束，不能單憑該結果證明後端已拒絕。
- 後續兩次等待晚到回應的腳本，在以 `response.text()` 比對中文錯誤時因回應字元解碼問題失敗；保留 [late-confirmed.json](late-confirmed.json)。人工檢查實際後端回應具有 `success:false`；測試資料庫唯讀檢查訂單仍為 2 筆、方案卡 1 張、3 筆取消意圖均無訂單。見 [late-inspection.json](late-inspection.json)。此交叉核對不替代原本失敗的精確中文訊息斷言。
- `results.json` 曾由競爭腳本的進度函式覆寫，故其 `complete:false` 是尚未完成的進度快照，不是正常流程原始結果；正常流程的 `complete:true` 與各計數曾輸出至執行工具。保留此檔以免掩蓋紀錄問題。

隔離 PostgreSQL 另一組服務測試見 `src/__tests__/beauty-online-real-postgres.test.ts`：實際 Prisma、交易鎖、建單、發卡及帳簿；登入身分／權限和通知發送為替身。測試使用 Prisma schema 產生新庫再套兩個意圖 migration，不是從正式歷史 schema 升級的驗證。
